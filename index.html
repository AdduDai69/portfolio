RISC vs. CISC: choosing a processor

A company has two systems, one RISC and one CISC, and must pick an instruction-set design for a low-power embedded device. This is written from standard computer-architecture knowledge. I ran no benchmarks, so there are no measured numbers here.

Case study questions

1. What is RISC? What is CISC?

RISC (Reduced Instruction Set Computer) uses a small set of simple, regular instructions. Typically only load and store instructions touch memory, arithmetic works on registers, and the register file is large. CISC (Complex Instruction Set Computer) offers many instructions, including powerful ones that do several steps at once, such as an arithmetic operation with a memory operand or a block copy. Instruction lengths and formats vary.

2. Why do many RISC instruction sets use fixed-length instructions?

The hardware always knows where the next instruction begins, so fetching and decoding are simple and can overlap across pipeline stages. There is no need to work out an instruction's length before starting the next one. The cost is lower code density, which compressed encodings such as RISC-V C or ARM Thumb partly win back.

3. How does instruction complexity influence instruction decoding?

The more formats, lengths and addressing modes there are, the more work the decoder does. Variable-length CISC decoding must find instruction boundaries first and often splits complex instructions into micro-operations or microcode. That takes more logic, area and power. RISC decoding is close to reading fixed bit fields.

4. Compare the typical addressing-mode approaches in RISC and CISC.

RISC offers few modes: register, immediate and base plus displacement, and only loads and stores access memory. CISC offers many, such as direct, indirect, indexed and base plus scaled index plus displacement (x86), and ALU instructions can take memory operands directly. CISC is more convenient for compilers and gives denser code. RISC is simpler to build and pipeline.

5. Can a CISC processor outperform a RISC processor? One reason.

Yes. Dense code means fewer bytes fetched per task, so there are fewer instruction-cache misses and less memory bandwidth used. That can win when performance is limited by memory rather than the core. Modern x86 chips also translate instructions into simple micro-ops, so the gap depends on the implementation as much as on the ISA.

(c) Recommendation: RISC for a battery-powered embedded device

Choose RISC, for example an ARM Cortex-M or a RISC-V core. A simpler decoder and regular pipeline need fewer transistors and less switching, which helps a device on a small battery. Execution time is also easier to predict. The weak point is code density, and compressed instruction modes largely fix it, which saves flash memory.

Caveats: power depends on the whole implementation and on how long the chip can sleep, not on the ISA label alone. If the product must run existing x86 software, CISC could still be the right call.
